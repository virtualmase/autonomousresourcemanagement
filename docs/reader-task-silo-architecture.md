# Reader-Task Silo and Interlinking Architecture

**Status:** Staged implementation; published routes verified on 2026-08-27, with source-only flagship and portal continuations retained pending their existing property decisions.
**Purpose:** Make the Virtualmase public work legible as a set of independent reader tasks. This is not a link-exchange scheme, a canonical-consolidation plan, or a claim of institutional endorsement.

## The content spine

The connective tissue is an **accountable-work thread**, not a marketing funnel: understand a system; bound an intended action; document a material change; inspect completed practice; correct or contribute through the property that owns the relevant record. A reader may enter at any point and should still receive a complete, useful answer.

| Silo | Primary reader question | Property that owns it | Original contribution | Deliberate non-role |
|---|---|---|---|---|
| **Orientation** | “Where does this public work live, and which route answers my question?” | Virtualmase directory | A concise map of independently useful properties and their status. | It does not repeat individual methods or definitions. |
| **Learning model** | “How do I understand resource boundaries, decision rights, and traceable records?” | AI Mastery | A teaching pathway, conceptual topology, and bounded practice. | It does not make an operational approval or publish a reference corpus. |
| **Action boundary** | “Before a workflow acts, what may it touch, who decides, and how is it interrupted?” | Action Boundary Brief | A pre-action documentation pattern and fictional walkthrough. | It does not approve actions or document later changes. |
| **Change continuity** | “What changed in an AI-enabled workflow, who owns the re-check, and how can it pause or return?” | AI Change Record | A post-change documentation pattern and fictional walkthrough. | It does not set an action boundary or certify a release. |
| **Public practice** | “What real work was completed, what evidence supports it, and how may it be corrected?” | ARM reference `/practice/` | Factual, source-linked work records with open questions. | It does not invent results, aggregate a portfolio, or replace source repositories. |
| **Reference and correction** | “What does ARM mean, what supports the definition, and how can I challenge it?” | ARM reference | Cited definitions, source notes, entity records, and correction pathways. | It does not become an executive campaign. |
| **Executive application** | “How should an operating owner frame a consequential autonomous workflow?” | `.xyz` flagship source | Executive decision practice, readiness questions, and original field guidance. | It does not repeat the learning or reference materials. |
| **Contribution** | “Where can a person propose, review, or maintain bounded work?” | Participation portal source | Governed participation, capability records, and contribution context. | It does not mimic a dashboard or claim a live collaborative service. |

## Contextual interlinking rules

Every outbound relationship must appear next to the reader task that creates it. Navigation may contain concise direct routes; a page-ending continuation block should contain no more than three choices. A comprehensive footer is a route index, not a collection of keyword anchors.

## Content priorities

The first original additions should be short **field notes**, each answering one reader question that is neither a generic definition nor a tool comparison.

| Priority | Working title | Owning property | Reader task | Required evidence boundary |
|---|---|---|---|---|
| 1 | **The handoff is part of the system** | AI Mastery | Distinguish an explanation from an accountable operational handoff. | Use cited learning sources and clearly labelled conceptual diagrams. |
| 2 | **What changes when the tool does not?** | AI Change Record | Recognize that a source, permission, monitor, or escalation route can materially change a workflow. | Use fictional, sanitized change cases; do not make tool-specific performance claims. |
| 3 | **A public record is not a public system log** | ARM reference / practice | Distinguish evidence-oriented public records from data collection or surveillance. | Cite research on post-deployment monitoring and state privacy limits. |
| 4 | **The interruption route** | Action Boundary Brief | State how a person can pause/challenge an action without becoming a rubber-stamp. | Use a conceptual escalation map and explicit no-approval boundary. |
| 5 | **From completed work to a correctable record** | Public practice | Explain how source evidence, outcome boundaries, open questions, and correction paths relate. | Cite only actual public records and repositories. |

## Acceptance checks

1. Every changed production page retains an exact self-canonical URL and its existing original reader role.
2. Every new cross-property link names the destination benefit in visible text; no generic `Learn more` label is used.
3. No page contains a cross-domain canonical, duplicated lead copy, invented result, tracking mechanism, unreviewed `Organization` claim, or coercive engagement pattern.
4. Every source-only flagship or portal update retains its clearly stated non-deployed/non-hostname status.
5. Each changed static package passes its local validator and relevant interaction checks before a focused source commit.
6. Public release remains owner-gated when it affects a new external project site, hosting connection, DNS, analytics, or Search Console mutation.
